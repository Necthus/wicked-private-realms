# 服务端权威状态同步改造方案

状态：已通过游戏进程内的独立会话模拟、快照往返、第二会话恢复、回环 TCP 弱网及跨进程输入/状态复制探针。独立 headless 真实游戏模拟尚未完成；按用户接受的备选路线提供 [两台电脑的房主模拟开发入口](AUTHORITY-LAN-TEST.md)。真实双机人工游玩、战斗和交互、正式权威存档仍待验收；默认服务端尚未切换模式。实测细节见 [本机可行性记录](AUTHORITY-FEASIBILITY.md)。

工作分支：`codex/server-authoritative-state-sync`。

## 目标与行为

由服主控制的模拟进程计算世界状态，包括移动、碰撞、战斗、AI、掉落和世界进度。玩家客户端提交操作意图，接收权威状态，并通过本地预测、校正和远端实体插值呈现游戏。

单个玩家的输入迟到或连接阻塞时，服务器按已定义的缺失输入规则继续推进，其他连接继续接收状态。网络恢复的玩家接受服务器状态并追赶。此目标隔离的是时间线停顿；迟到玩家的行为仍会影响共同世界中的交互。

不能把玩家客户端上传的位置、血量或完整快照直接作为最终结果，也不能只把现有输入转发模式改名为“服务端权威”。

## 已确认的代码边界

| 当前模块 | 已有能力 | 本次改造缺口 |
| --- | --- | --- |
| `server/room_simulation.py` | 汇总确认输入、广播、历史缓存、入场快照转交 | 没有运行游戏世界模拟；推进依赖所有活跃玩家的输入进度 |
| `server/transport.py` | Photon/Quantum 消息路由、房间与连接管理 | 需要接入模拟进程及状态下发；慢连接发送不能阻塞房间 |
| `server/quantum_wire.py` | 输入帧及 Quantum 控制消息编码、快照封装 | 不解析快照中的实体状态；没有持续状态复制及客户端校正实现 |
| `native/adapter/adapter.c` | 登录、后端地址和 Photon 连接适配、生命周期钩子 | 没有持续权威状态接收、应用与预测校正钩子 |
| `native/host/GameProcess.cs` | 启动已安装的游戏并注入适配器 | 当前是玩家游戏宿主，尚不是已验证的专用模拟运行时 |
| `server/shared_saves.py` | 玩家声明一致后提交客户端提供的存档 | 需要由权威模拟产生世界与角色状态，并明确账号归属 |

现有 `FrameSnapshot` 路径从已在线玩家获取快照，用于新玩家入场和输入历史追赶。消息能被转发，不代表已经验证可在游玩过程中高频恢复快照、校正预测并保持画面连续。

仓库没有独立游戏模拟源码或已验证的专用服务端运行时。适配器依赖 v29466 的特定 `GameAssembly.dll`，不能单靠现有 Python 模块实现完整游戏规则。

## 目标结构

```text
玩家游戏与适配器
  ├─ 上行：操作意图、序号、模拟帧与接收确认
  └─ 下行：权威状态、已处理输入序号与会话控制
             │
       私服网关 / 会话服务
             │
       服主控制的模拟进程
         ├─ 按服务器时钟推进世界
         ├─ 裁定游戏结果并生成状态
         └─ 产生可持久化的世界与角色数据
```

账号、成员、TLS 接入和数据库存储层可以作为基础继续使用；实时模拟、状态同步、客户端校正和存档生产需要另行实现或适配。具体协议及兼容版本必须显式区分，不能向旧客户端发送未支持的状态消息。

## 第一阶段：验证模拟与校正入口

这是后续工作依赖的可行性验证，尚未通过。

1. 查明能否复用现有游戏运行时，在服主控制的进程中加载真实国度，并在没有玩家参与计算的情况下持续推进。独立无头运行未验证；先验证专用游戏进程是否可行，不预设 Linux、无显卡或低内存部署能力。
2. 核对帧推进、玩家输入注入、完整状态导出与恢复入口，以及资源、线程、场景和运行时依赖。游戏文件由部署者提供，不加入源码和发布包。
3. 验证客户端能否在真实游玩过程中接受服务器状态，回到正确帧，再重放未确认的本地输入。必须覆盖游戏内部系统状态，不能只修改可见坐标。
4. 用两个玩家客户端和一个专用模拟进程验证移动、战斗与实体生命周期。人为延迟一个玩家的输入，确认服务器和另一个玩家仍持续推进。

通过条件：独立模拟可以推进真实世界；导出和恢复后的状态一致；客户端持续校正不会破坏战斗或实体状态。记录具体入口、构建指纹和实测依赖后再决定运行时方案。

如果无法复用运行时，需要先解决模拟运行环境或重建游戏逻辑的问题；空的 Python 世界模型不能替代真实游戏验证。

## 第二阶段：实时会话与状态复制

在第一阶段通过后实现：

- 服务器时钟驱动模拟，沿用已核对的游戏逻辑步长；状态发送频率和带宽预算通过实测确定。
- 输入包含身份绑定、递增序号与目标帧；限制未来帧、处理重复和迟到输入，并在状态中确认已处理的输入。
- 明确缺失输入语义。区分可延续的移动与一次性动作，避免重复攻击、消耗物品或交易。已确认历史不因任意迟到输入被直接改写。
- 从权威模拟产生初始完整状态，再评估增量状态、基线确认、丢失基线恢复及分包。实体创建、销毁、稳定标识与场景切换必须一并处理。
- 每个连接独立排队发送；定义积压上限与恢复策略。可替换的旧状态和必须可靠交付的事件分别处理，慢连接不能持有房间模拟锁等待网络写入。
- 客户端以权威状态为基准校正本地预测，对远端实体插值。优先验证已有 Quantum 运行时的恢复能力，不能假定简单重定向连接即可完成。
- 传输选型另行实测。现有 TCP 通道可以用于原型；是否引入 UDP 等传输，与服务器是否运行权威模拟是两个独立问题。

## 第三阶段：存档、入退场与故障恢复

- 由权威模拟导出世界和角色数据，复用已有存储事务及账号归属校验，替换当前依赖玩家一致声明的存档生产流程。
- 新玩家和重连玩家从服务器获得状态与必要的后续数据，不再依赖某位在线玩家供应快照。
- 定义模拟进程退出、重启、加载失败和存档失败时的会话行为，避免把过时状态覆盖到更新的存档。
- 新协议客户端和服务端版本配套发布。部署需要的游戏资源、操作系统及资源消耗，以第一阶段验证结果为准。

## 验收

- 延迟、抖动、丢包或暂停一个玩家的输入时，服务器模拟与其他玩家持续前进。
- 一个客户端不再读取数据或发送队列积压时，不阻塞模拟及其他连接。
- 网络恢复后，落后玩家恢复到权威世界；移动、血量、敌人、物品与交互状态保持一致。
- 重复或迟到的一次性操作不会造成重复伤害、重复消耗、重复掉落或重复交易。
- 覆盖中途加入、断线重连、场景切换、死亡重生和实体销毁后的状态恢复。
- 保存、退出并重启后，世界与角色恢复正确，物品和账号归属不被串用。
- 协议单元测试、故障注入测试及真实多进程游戏验证分别记录；合成世界测试不能视为真实游戏改造已完成。

## 改动量判断

这是跨服务端、游戏运行时、原生适配器和存档流程的架构改造，客户端和服务端都需要更新。最大不确定性在于复用游戏模拟与持续校正的入口，而不是网络消息封装。

第一阶段实测完成前，不给完整迁移的固定工期或代码行数承诺。本方案文件与工作分支不代表运行中的服务器已切换模式。
